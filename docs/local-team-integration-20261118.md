# 팀원 PR을 합친 로컬 통합본 (2026-11-17~18)

다섯 저장소의 최신 develop과 팀원이 올린 열린 PR을 로컬 브랜치 `chore/local-team-e2e-20261117`에 합쳤다. 원격 develop 병합이나 push는 하지 않았다. 기존 사진·상태 설명 충돌 확인 기능도 보존했다.

## 무엇을 합쳤나

| 저장소 | 추가로 합친 팀원 PR | 내용 |
| --- | --- | --- |
| scrap-web | #55 | 판정 결과에서 신고 서류 만들기 화면 연결 |
| scrap-server | #54 | 신고서·처리계획서·수탁확인서 초안 생성 및 미리보기 |

| scrap-route | #23 | 예전 KG 개발용 탐색 도구. 현재 업체 추천의 실행 경로에는 연결하지 않음 |
| scrap-infra | #13 | 선택적 Azure Document Intelligence OCR 환경변수 전달 |

이미 develop에 병합된 기존 PR은 최신 develop으로 받았다. 사용자 본인의 오래된 미병합 route 초안 PR은 팀원 PR로 간주하지 않았으며, 현재 기능을 되돌리는 재병합은 하지 않았다.

## 병합하면서 고친 부분

- 문진의 코드 없는 결론에서 `reason`을 두 번 전달해 오류가 나는 문제를 수정했다.
- 새 유기용제 혼합 질문에 설명·선택지 안내·확인 방법을 넣었다.
- 오래된 산 혼합 시험 입력을 최신 `chemical_itself` 질문과 맞췄다. 기존 분류 결과와 보류 원칙을 유지한다.
- 서버 할 일 번호 충돌을 정리했다. 팀원 서류 기능은 T-166, 기존 사진 충돌 확인 기능은 T-170이다.
- 예전 문진 참조 웹을 되살리지 않았으며 UI는 scrap-web에 둔다.

## 실행

이 문서가 있는 scrap-infra에서 실행한다. 기존 `.env`와 DB 볼륨을 유지한다.

```powershell
docker compose up -d --build
docker compose run --rm server-seed
docker compose exec -T server python -m app.domains.transport.dev_accounts
```

브라우저는 **http://localhost:5178**로 연다. 서버 8000 → 문진 8030 / 경로 8010으로 연결한다. `127.0.0.1`로 바꾸지 않는다.

이번 seed는 공정 69개·검수 업체 62곳을 적재했다. 기존 업체 명부는 유지했으며 명부 전체를 새로 수집·검증했다는 뜻은 아니다. 병합 전 서버·문진 DB 백업은 저장소 밖 `output/team-merge-backups/`에 보관했다.

## 실제 웹 검증

실제 업체가 아닌 별도 개발용 A/B/C 기업 계정과 합성 물량을 사용했다. 브라우저 입력과 클릭으로 진행했고 DB에서 완료 상태를 강제로 바꾸지 않았다.

### 새 문진 → A→B→C

- A: `e2e-20261117-a@example.com`, B: `pp-sort@example.com`, C: `pp-pellet@example.com`.
- 새 PP 버튼 문진 8회 → 51-03-01 확정 → 제조 잔재·스크랩 선택 → 1,000kg 등록.
- 첫 단계 공정 5개·업체 14곳을 조회하고 **14/14 Azure 검토 완료**. 화성 출발에서 새롬 화성까지 OSRM 도로거리 16.3km 표시.
- B 조건부 수락 → A 합성 자료 제출 → B 최종 수락 → A QR 발급 → B 계정으로 QR 링크를 열어 입고 확인.
- B가 PP 파쇄품 950kg·상태·근거를 기록. **B 위치**에서 다음 후보 9곳을 찾아 **9/9 Azure 검토 완료**. 독산 화성까지 도로거리 17.7km 표시.
- C 조건부 수락 → B 자료 제출 → C 최종 수락 → B QR 발급 → C 계정 입고 확인.
- C가 PP 펠렛 900kg과 완료 근거를 기록하고 완료. A 계정에서도 완료 상태, 두 업체 입고, 전체 15건 이력을 확인했다.
- 새 case: `00707d89e8e248dfb5f187e9c33c267a`, lot: `5d0ab24d-268b-48f6-8952-8eaa5cf319ad`.

### 기존 저장 건 → 한 업체에서 바로 완료

- 병합 전에 사진·상태 설명 불일치를 확인하고 수정·재검토한 기존 PP 파쇄품 950kg 건을 사용했다. 사진·확인 이력이 유지되는지 검증하는 목적이다.
- 인수 요청 이후를 이번 통합본에서 실행: 조건부 수락 → 자료 제출 → 최종 수락 → QR 입고 → 펠렛900kg → 완료.
- 최초 배출 A에서도 완료 및 11건 이력이 보였다. 중간업체를 추가하지 않았다. 수신 계정 이름은 C이지만 이 시나리오에서는 첫 수신업체(B 역할)다.
- 기존 case: `36a09fc25406427b96b91a79262095a6`, lot: `858d3bef-aac2-4985-b535-c292e1b1cf94`.
- 이 건의 문진·사진 Azure 분석은 이전 실행 기록이다. 이번에 새로 수행한 A→B→C 검증과 구분한다.

### 팀원 서류 기능

새 문진에서 연결되는 서류 화면을 열어 회사 정보·판정이 연결되는 것을 확인했다. 제5호 초안을 서명 없이 PDF·HWPX로 받았다. PDF 3쪽을 읽을 수 있고 HWPX ZIP 및 section XML이 정상이다. 서명·기관 제출은 하지 않았다.

화면 증거는 저장소 밖 `output/team-merge-e2e/`의 `a-completed.jpg`, `a-completed-ui.txt`, `a-direct-completed-ui.txt`, `legal-form-ui.txt`에 있다.

## 아직 별도 확인할 것

- OCR 연결 설정은 병합했지만 이 실행의 Document Intelligence OCR은 기본 비활성이다. 스캔 성적서 실호출 성공으로 보고하지 않는다.
- Google/Microsoft 소셜 로그인 대신 개발용 로그인으로 시험한다.
- QR은 수신 계정으로 링크를 열어 시험한다. 휴대전화 카메라 인식·실제 운송은 시험하지 않는다.
- 공개 자료 AI 검토나 가상 계정 수락은 실제 업체의 허가·반입 승인·계량 증빙 검증을 대신하지 않는다.
- 현재 화면의 경로 지도 선은 확인된 사업장 연결이다. 후보 거리 계산은 OSRM 자동차 경로이며 화물차 통행 제한·실제 운송 GPS 경로와는 다르다.
