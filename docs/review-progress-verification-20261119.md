# 거리순 업체 검토·예정 경로 검증 (2026-11-19)

## 바뀐 흐름

문진 확정 → 물량·사진 등록 → 전체 연결 업체의 도로거리 조회 → 가까운 서로 다른 5개 사업장 AI 검토 → 제한·근거 부족·AI 미완료가 있으면 뒤 후보 검토 → 확인된 업체만 표시 → 사용자가 인수 요청 → 업체 수락 → 운송·QR 입고.

5곳은 목표 수입니다. 근거가 확인된 곳이 적으면 그 수만 보여줍니다. 미검토·근거 부족·도로거리 미확인 업체는 별도 목록에 남고, 부적합으로 단정하지 않습니다. 업체의 최종 반입 수락은 그대로 필요합니다.

사진은 Azure가 한 번 관찰하고, 같은 관찰 결과를 업체별 근거 대조에 사용합니다. 사진 모델에는 상태 설명·업체 근거를 주지 않습니다. 분류번호를 사진으로 바꾸지 않습니다. 사진·입력·근거·모델/지침이 바뀌면 필요한 부분을 다시 확인합니다. 폐기물 사진이 아니면 업체 비교 전에 중단합니다.

## 로컬 실제 확인

| --- | --- |

| 진행 표시 | 기존 아고라 Thinking Orb 원본 사용. 서버의 도로거리/사진/업체 검토/저장 단계와 실제 건수 표시, 새로고침 후 진행 유지 |
| 요청 직후 지도 | 수락·운송 시작 전 A·B 핀과 카카오 예정 도로 경로 약 6.5km 표시, 예정은 점선 |

| A 완료 조회 | A 계정의 처리 완료 이력에 독산 화성·펠렛 95kg·기록 보기 표시, 공유 인계 이력 확인 |

A는 엔피씨 주식회사 화성 사업장, B 후보는 독산 화성의 공개 사업장 정보를 사용했습니다. 로그인 계정과 업체 연결, 물량 100kg, 상태 설명은 로컬 합성 시험입니다. 사진은 기존 공개 PP 연구 사진이며 실제 거래 물량이 아닙니다. 실제 업체 연락·계약·운송·허가 확인을 수행한 결과가 아닙니다.

## 자동 검증

- server: 전체 637개 통과. 마지막 작업 선점 잠금 보완 후 관련 5개 재검증 통과. Ruff 검사·전체 포맷 검사·에이전트 문서 동기화 검사 통과.
- route: 전체 584개 통과, 72개 건너뜀, 하위 검증 24개 통과. Ruff 검사·전체 포맷 검사 통과.
- web: 동료의 지원 소재 제한 변경까지 병합 후 102개 통과, Docker 프로덕션 빌드 통과.
- infra: Compose 설정 검사와 통합 서비스 시작 확인.
- 4개 PR의 GitHub CI 통과: server PostgreSQL 검사/route 단위·Neo4j 검사/web 빌드·테스트/infra 설정 검사.
- 기존 의존성 Authlib/Starlette의 사용 중단 경고와 웹 큰 번들 경고가 남습니다. 건너뛴 route 테스트는 통과로 세지 않습니다.

자동 검증에서는 정상 5곳에서 중단, 뒤 후보 보충, 사업장 중복 제거, 보충 후보 순위 재계산, 근거가 없으면 0곳, 거리 미확인 별도 보존, 잘못된 사진 조기 중단, 업체별 입력/모델 변경에 따른 캐시 무효화, 작업 중복·접근 격리·중단 복구·오래된 물량 결과 차단, B→C 출발점과 거절/취소 제외를 확인했습니다. 이 전체 조합을 실제 Azure/웹으로 모두 수행했다는 뜻은 아닙니다.

## 적용 순서

1. scrap-route: 검토 버전 조회·사진 단독 관찰·관찰 재사용 API.
2. scrap-server: 저장형 검토 작업, 도로거리순 5곳 검토·보충, 예정 경로 API.
3. scrap-web: 새 작업 API를 쓰는 Orb와 예정/운송 경로 화면.
4. scrap-infra: route 건강 확인 후 server 시작, 아래 순서로 재빌드.

```bash
docker compose up -d --build route
docker compose up -d --build server
docker compose up -d --build web
```

추가 큐·마이그레이션·새 키는 없습니다. 기존 카카오/모델 설정을 사용합니다. 기존 동기 `/candidates` API는 전체 후보 검토 방식으로 호환 유지하며, 새 웹이 `/review-jobs`를 사용해야 최적화·진행 조회가 적용됩니다. develop 병합만으로 운영 도메인이 바뀌지는 않습니다. 운영은 팀의 main 릴리스 절차가 별도로 필요합니다.

관련 PR: [route #69](https://github.com/BluberrypAI/scrap-route/pull/69), [server #61](https://github.com/BluberrypAI/scrap-server/pull/61), [web #66](https://github.com/BluberrypAI/scrap-web/pull/66).

DB 작업 선점은 서버 복제본 사이에 적용하지만 모델 동시 호출 상한 3은 route 프로세스별입니다. 운영 전체 Azure 할당량을 관리하는 분산 큐는 후속 범위입니다. 예정 경로는 카카오 자동차 거리 우선 계산이며 화물차 전용 제한이나 실제 차량 GPS 기록이 아닙니다.

## 후속: 여러 물량에서 공개 근거 재사용

route/server/web의 같은 PR에 공개 근거 공용 캐시와 SCRAP 보라색 Orb를 추가했습니다. 기존 PostgreSQL `treatment_snapshots`를 사용해 새 migration·키는 없습니다. 공개 근거는7일 유효·최대1024건이며 출처·검토 버전이 바뀌면 다시 확인합니다. 사진·상태·기업별 답변·물량 판단은 공용으로 저장하지 않습니다.

실제 Azure PP9개 후보 측정: 공용 캐시를 처음 채우는 실행85.729초, 설명이 다른 새 물량35.629초(공개 추가 호출0회·사진1회·물량1회)였습니다. 서버 재생성 뒤 새 웹 PP 문진/물량에서도 공개 캐시9건 재사용·공개 추가 호출0회로 약39.75초, 정확히 같은 웹 입력 재검토는 약3.93초·모델 호출0회였습니다. 한 번의 합성 시험이며 고정 응답시간이나 실제 업체 수용 검증을 뜻하지 않습니다.

server642개 / route588개(+하위24개·환경 의존skip72) / web102개 통과. 새 문진→물량→공개 PP 사진→검토에서 보라색 Orb·진행 문구·재사용 표시와 후보1곳의 인수 요청 버튼을 확인했습니다. 공개 근거의 만료를 기존 물량 캐시로 우회하지 않는 것도 검사했습니다. 자세한 범위는 scrap-server `docs/public-review-cache-validation-20261119.md`에 있습니다.
