# PP 시연 두 가지 — 최신 통합본

브라우저는 **http://localhost:5178**을 사용한다. 모든 물량·품질 수치·수락은 개발용 합성 시험이며 실제 업체와 거래하지 않는다. 분류 결과는 검토 전 참고 판정이고, AI 공개 자료 검토와 업체의 실제 반입 승인은 다르다.

## 공통 준비

- `scrap-infra`에서 `docker compose up -d --build`로 실행한다. 기존 `.env`와 DB 볼륨을 유지한다.
- 출발 A: `e2e-20261117-a@example.com` — 가상 화성 제조기업.
- 전처리 B: `pp-sort@example.com` — 새롬 화성 시험 연결.
- 재생 업체: `pp-pellet@example.com` — 독산 화성 시험 연결.
- 두 수신 계정은 역할 확인용 가상 계정이다. 첫 시연에서는 재생 업체가 B이고, 두 번째에서는 C다.
- 서로 다른 브라우저 프로필/시크릿 창으로 A와 수신 기업에 로그인한다. 같은 프로필의 탭만 두 개 열면 로그인 쿠키를 공유한다.
- QR은 수신 기업이 로그인한 브라우저에서 연다. 발송 기업 A로 입고를 확인하지 않는다.

## 시연 1: A → B, 한 업체에서 완료

**이야기:** A가 이미 분리·세척·파쇄한 PP를 보낸다. B가 펠렛으로 재생하므로 다른 업체 C가 필요하지 않다.

1. A가 새 문진에서 PP 파쇄품·고체·일반 제조공장·하루 300kg 이상·유해 오염 없음 등의 상태를 설명한다. 추가 질문에 답하고 51-03-01 판정을 확인한다.
2. 처리 경로에서 **파쇄품**을 선택한다. 중량 1,000kg과 현재 상태를 등록한다.
3. 업체 검토를 실행한다. 공개 근거·미확인 반입 조건·도로거리를 보고 **독산 화성**에 요청한다.
4. B 계정(`pp-pellet@example.com`)이 확인 후 수락한다. 조건부 수락이면 A가 자료를 제출하고 B가 확인한다.
5. A가 입고 QR을 발급한다. B 계정에서 QR 링크를 열어 실물을 받았다는 입고 확인을 누른다. 현재 QR 화면은 별도 실측 중량을 입력받지 않는다.
6. B가 최종 산출물 **PP 펠렛 920kg**, 처리·품질 근거를 기록한다. 종료 조건을 확인하고 처리완료한다.
7. A에서 완료 상태와 B의 입고·처리 이력을 보여준다.

**설명할 핵심:** 같은 PP라도 이미 전처리된 물량은 재생 업체로 바로 보낼 수 있다. QR은 입고 확인이고, 처리완료는 별도 산출물·근거 기록이다.

## 시연 2: A → B → C, 산출물에 따라 다음 단계 결정

**이야기:** A의 PP 사출 잔재에는 라벨·먼지가 있어 전처리가 필요하다. B가 처리한 뒤 실제 산출물을 기록하면 그 상태를 기준으로 C를 다시 찾는다.

1. 새 문진으로 PP 사출 잔재를 분류하고 **제조 잔재·스크랩** 1,000kg을 등록한다.
2. 업체 검토 후 새롬 화성 시험 계정 B에 요청한다. 조건 확인·수락·A의 QR 발급·B 입고까지 진행한다.
3. B가 처리 후 **PP 파쇄품 950kg**과 실제 상태·근거를 기록한다.
4. B 위치와 산출물 기준으로 다음 후보를 검토한다. 독산 화성 시험 계정 C에 요청한다.
5. C 수락·B QR 발급·C 입고 후 **PP 펠렛 900kg**과 완료 근거를 기록한다.
6. A에 다시 로그인해 두 업체의 입고와 전체 처리 이력을 확인한다.

**설명할 핵심:** A가 처음부터 C까지 확정하지 않는다. B의 실제 산출물과 수신 기업의 동의가 다음 단계를 결정한다.

## 이번 실행 결과

2026-11-18 오후 최신 develop 통합본에서 **두 시나리오 모두 새 문진부터 실제 웹 버튼으로 완료**했다. 각 수신 계정으로 로그아웃·재로그인해 권한을 바꿨으며, 서버 API로 단계 상태를 강제로 만들지 않았다. 문진과 업체 검토는 Azure 실호출이다.

| 확인 항목 | 시연 1 A→B | 시연 2 A→B→C |
|---|---|---|
| 문진 판정 | PP / 51-03-01 | PP / 51-03-01 |
| 처음 물량 | 세척·파쇄품 1,000kg | 사출 잔재 1,000kg |
| AI 검토 | 공정·업체 조합 9/9 완료 | A에서 14/14, B 산출물로 9/9 완료 |
| 수신 기업 동의 | 조건부 수락→자료 제출→최종 수락 | A→B와 B→C 모두 같은 순서 통과 |
| QR | A 발급→수신 계정 입고 확인 | A 발급→B 입고, B 발급→C 입고 |
| 실제 기록한 산출물(합성 시험값) | 펠렛 920kg | B 파쇄품 950kg→C 펠렛 900kg |
| A에서 확인 | 완료, 이력 8건, 입고 사업장 1곳 | 완료, 이력 15건, 입고 사업장 2곳 |

검토 완료는 모두 반입 적합 판정을 받았다는 뜻이 아니다. 예를 들어 새롬의 공개 근거 추가 확인 표시를 유지한 상태에서 가상 수신기업이 이번 시험 물량의 조건을 확인했다. 실제 업체의 허가·반입 승인으로 해석하면 안 된다.

### 완료 화면 바로 열기

A 계정으로 로그인한 뒤 아래 페이지를 연다. 두 건 모두 현재 로컬 DB에 보존되어 있다.

- 시연 1: http://localhost:5178/wastes/case-fc126de95e7c4913a8088852e12e95f6
- 시연 2: http://localhost:5178/wastes/case-45f48ed12f944abc97048b7055462b6c
- 시연 1 lot: `d107bc10-2310-467d-b050-17f4d52b8852`
- 시연 2 lot: `887accb2-c747-484f-91e4-f265ad03a5b2`

완료 건은 재실행용 초기 상태가 아니다. 처음부터 시연할 때는 새 문진을 만든다. QR 링크의 토큰은 문서에 저장하지 않는다.

### 거리와 모니터링의 차이

후보 비교에서 독산 화성까지 A 출발은 OSRM 도로거리 12.9km, B 새롬 출발은 17.7km로 표시됐다. 반면 완료 이력 지도에 그어진 선은 입고 확인 사업장 간 직선 연결이다. 실제 차량 GPS 이동 기록이 아니다.

### 이번에 고친 표시 오류

입고 전 인수 요청·조건부 수락·QR 대기 카드가 넓은 상태 분류인 '처리 진행'만 보고 처리 중처럼 보였다. `scrap-web`에서 서버의 구체적인 안내 문구와 실제 인계 상태를 우선하도록 수정했다. 재빌드 후 웹에서 '인수 수락 · 입고 대기 / 입고 QR을 발급해 물량과 함께 보내 주세요'를 확인했다. 공장 가동 애니메이션도 실제 processing 상태에서만 시작한다.

### 검증 범위와 남은 구분

- 개발용 계정 로그인과 QR 링크로 입고를 검증했다. 실기업 승인·소셜 로그인·휴대전화 카메라 스캔·실운송은 이번 검증 범위가 아니다.
- 이번 두 시나리오는 상태 설명으로 진행했고 사진을 새로 업로드하지 않았다. 사진 분석 기능이 없다는 뜻은 아니지만 사진 AI 검증까지 재시험했다고 주장하지 않는다.
- 산출물 감소분 80kg/50kg 등은 합성 설명에 남겼다. 잔재물의 별도 로트와 질량수지 전체 추적까지 검증한 것은 아니다.
- PP 두 대표 흐름 통과가 모든 재질·모든 업체의 실제 처리 가능성을 보장하지 않는다.
- 실행 증거(화면·DOM·테스트 로그)와 실행 전 DB 백업은 상위 폴더 `output/latest-e2e-20261118/`에 로컬 저장했다. 백업에는 기존 데이터가 있으므로 Git에 올리지 않는다.
